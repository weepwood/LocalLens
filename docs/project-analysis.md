# LocalLens 项目分析与演进建议

## 当前定位

LocalLens 已经完成了一个可验证的最小闭环：Windows 上的 Go 服务扫描本地图片和视频，使用 SQLite 建立索引，并通过局域网向 Flutter Windows / Android 客户端提供缩略图、原图和视频 Range 流。

这个方向成立，但当前版本更接近“技术原型”，距离稳定的家庭媒体库还有三层差距：大规模媒体浏览体验、可靠的后台索引能力，以及设备级安全与远程访问能力。

## 当前优势

1. **边界清晰**：原始媒体仍由 Windows 文件系统管理，服务端只维护索引与缓存。
2. **部署成本低**：Go 单文件服务端配合 SQLite，不需要独立数据库服务。
3. **播放链路正确**：视频通过 HTTP Range 读取，支持进度跳转，避免整文件下载。
4. **跨平台方向合理**：Flutter 客户端可以复用 Windows、Android 和后续 iOS 业务代码。
5. **已有发布闭环**：GitHub Actions 能构建 Windows 服务端、Windows 客户端和 Android APK。

## 主要问题

### 1. 客户端只展示首批数据

旧版客户端每次固定请求最多 200 条媒体，没有继续加载机制。媒体数量达到几千或几万后，大部分内容不可见。

本次已实现：

- 每页 100 条的增量分页；
- 滚动接近底部自动加载；
- 加载失败后的手动重试；
- 已加载数量与媒体总数显示；
- 搜索请求防抖，减少连续输入导致的重复请求。

### 2. 扫描过程不可见

旧版服务端已经提供扫描启动和状态接口，但客户端没有使用，用户不知道扫描是否正在进行，也无法主动刷新媒体库。

本次已实现：

- 客户端启动扫描；
- 每两秒轮询扫描状态；
- 展示当前媒体库、发现数、索引数、失败数和进度；
- 扫描完成后自动刷新媒体列表和媒体库状态；
- 下拉刷新同步更新服务端状态与媒体内容。

### 3. 网络失败反馈过于模糊

旧版主要直接显示底层异常，且请求没有统一超时。

本次已实现：

- 连接超时与单次请求超时；
- Socket、TLS、HTTP、超时和 JSON 解析错误的中文提示；
- 媒体列表失败与服务器状态失败分离，服务器状态读取失败不会清空已有媒体。

### 4. 服务端仍是单文件实现

`server/main.go` 同时承担配置、数据库迁移、扫描、HTTP 路由、鉴权、缩略图与文件流。MVP 阶段可以接受，但继续增加收藏、标签、相册、设备令牌和转码后会迅速失控。

建议在下一阶段拆分：

```text
server/
├── cmd/server/
├── internal/config/
├── internal/database/
├── internal/library/
├── internal/media/
├── internal/scanner/
├── internal/thumbnail/
├── internal/streaming/
├── internal/auth/
└── internal/httpapi/
```

拆分时应先保持接口行为不变，再逐模块迁移，避免一次性重写。

## 功能优先级建议

## P0：稳定可用

### 媒体库过滤与游标分页

当前服务端采用 `LIMIT/OFFSET`。数据量很大且翻页很深时，SQLite 需要跳过大量记录。建议增加：

```http
GET /api/v1/media?libraryId=main&type=image&cursor=<modifiedAt,id>&limit=100
```

排序键使用 `(modified_at DESC, id DESC)`，返回 `nextCursor`。同时修正文档与实现不一致的问题：API 文档列出了 `libraryId`，当前服务端查询尚未真正处理该参数。

### 文件变化监听

增加 `fsnotify`，将实时监听作为增量更新手段，同时保留启动校验与定期完整扫描。事件应先进入防抖队列，等待文件大小稳定后再索引，避免正在复制的大视频被提前处理。

### 缩略图任务队列

当前缩略图在 HTTP 请求中同步调用 FFmpeg。多个手机快速滚动时会并发启动大量 FFmpeg 进程。建议改为：

- 固定数量 Worker；
- 相同缩略图请求合并；
- 请求未完成时返回 `202 Accepted` 或占位图；
- 失败任务带重试次数和冷却时间；
- 缓存清理采用 LRU 或磁盘上限。

### 数据库迁移版本

引入 `schema_migrations` 表，不再把所有建表语句直接放在启动函数中。每次新增字段都必须有版本化迁移和回滚说明。

## P1：核心媒体管理

### 收藏、评分、标签与相册

建议首先实现数据库虚拟分类，不修改原始文件：

```text
media_favorites
media_ratings
albums
album_items
tags
media_tags
```

优先接口：

```http
PUT    /api/v1/media/{id}/favorite
DELETE /api/v1/media/{id}/favorite
GET    /api/v1/albums
POST   /api/v1/albums
POST   /api/v1/albums/{id}/items
```

### 时间线

索引需要同时保存：

- 文件修改时间；
- EXIF 拍摄时间；
- 视频容器创建时间；
- 最终用于时间线的 `captured_at`；
- 时间来源 `captured_at_source`。

不能直接把文件修改时间等同于拍摄时间，否则文件复制后时间线会错乱。

### FFprobe 元数据

后台提取图片宽高、视频时长、分辨率、编码、帧率、音轨和字幕。元数据提取失败不应阻塞基础索引。

### 播放历史

记录每个客户端的最后播放位置，支持手机和 Windows 继续播放：

```text
playback_progress(device_id, media_id, position_ms, updated_at)
```

## P2：设备与网络

### 二维码配对

不要长期让用户手工复制统一 API Token。应实现：

1. Windows 端生成短时一次性配对码；
2. 手机扫码提交设备信息；
3. 服务端签发独立设备令牌；
4. Windows 端可查看并撤销每台设备；
5. 令牌只保存哈希，原文只在签发时展示一次。

### HTTPS 与证书指纹固定

局域网 HTTP 可以用于开发，但设备令牌与私人媒体不应长期明文传输。可在首次启动生成自签名证书，二维码中携带证书 SHA-256 指纹，Flutter 客户端完成指纹固定。

### 外网访问

不建议直接开放服务端口。优先支持 Tailscale / WireGuard 等可信 VPN，并在文档中明确公网端口映射不属于推荐方案。

## P3：高级能力

- 图片感知哈希与近似重复检测；
- OCR 本地文字搜索；
- 人脸聚类，但默认关闭并明确数据只在本地；
- HLS 按需转码与转码缓存；
- 视频时间轴缩略图；
- 地图视图；
- Windows 托盘管理端与 Windows Service；
- 电视端和浏览器只读客户端。

## 性能指标建议

后续开发不应只以“功能能运行”为验收标准，建议建立以下基准：

| 场景 | 建议目标 |
|---|---|
| 10 万媒体冷启动读取索引 | 2 秒内进入可浏览界面 |
| 媒体列表 API P95 | 200 ms 内 |
| 已缓存缩略图 P95 | 100 ms 内开始响应 |
| 扫描期间列表查询 | 不出现明显阻塞 |
| 手机快速滚动 | 不批量加载原图，不出现持续掉帧 |
| 服务异常退出 | SQLite 索引可恢复，无原始媒体损坏 |

## 安全原则

1. 客户端永远不能提交任意 Windows 绝对路径读取文件。
2. 所有媒体访问都必须先通过数据库媒体 ID 找到受控根目录。
3. 删除、移动、重命名应与只读浏览权限分开。
4. 默认只监听局域网，外网访问必须显式配置。
5. 日志不得记录 Token、完整 Authorization Header 或私人文件名搜索词。
6. 原始文件操作失败时，不能先更新数据库再操作磁盘。

## 推荐的下一次迭代

下一版建议聚焦服务端基础设施，而不是同时加入 AI：

1. 拆分 Go 单文件结构；
2. 增加数据库迁移版本；
3. 实现 `libraryId` 过滤和游标分页；
4. 引入文件监听和缩略图任务队列；
5. 加入收藏和播放进度；
6. 发布 `v0.2.0`，再开始二维码配对。
